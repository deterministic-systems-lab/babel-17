# B17-1: the second subset

**Status:** Draft, version 0.1. It freezes together with its accept/reject suite once WP3's checker agrees with every tier 0 label in it, as B17-0 did (D44, D65). Its own decisions, D81–D92, D99, D100 and D102 (§14), were accepted on 2026-10-28 and 2026-10-29.

**Implements:** D79, B17-1's scope, and D80, its verification levels. It defines B17-1's part of interfaces 1 (the grammar) and 6 (core terms), and the changes to interfaces 10 and 11 that B17-1 needs (D27).

**B17-1 is B17-0 plus this document.** Every rule of `docs/b17-0.md` holds unless a section here changes it, and its section numbers are the ones cited below. Every B17-0 program in the suite and the core library is a B17-1 program with the same meaning. A B17-0 program in general may not be: it may use a word B17-1 reserves as a name (§2), or read a new vector as a temporary, as in `(len (vec-new))`, which §5's rule 7 rejects. So the tools are told which subset they read (D101).

B17-1 keeps B17-0's three ideas and extends each:
- **Value semantics.** Tuples and data values are plain values, and the verifier encodes them as SMT datatypes, still with no heap.
- **Ownership without lifetimes.** Nested values are reached through places (§5), which never outlive the expression that names them, so no lifetime is ever needed.
- **No runtime error the verifier hasn't ruled out**, at L2 and above. Below L2, D80's levels say what an unproved goal does (§10).

## 1. A program

Insertion into a binary search tree, AlgoVeri's `bst_insert`. The person signs the `data`, the `ghost-fn`s and the `spec`; the agent writes the `def`.

```
(module bst_insert
  (header
    (purpose "Insert a value into a binary search tree.")
    (invariants "The result is a search tree holding the old values and the new one.")
    (failures "Allocation failure aborts."))
  (data tree () (leaf) (node (val i64) (left tree) (right tree)))
  (ghost-fn view ((t tree)) (iset int) (decreases (rank t))
    (body (match t
      (case (leaf) (iset-lit))
      (case (node v l r) (union (union (view l) (view r)) (iset-lit v))))))
  (ghost-fn is_bst ((t tree)) bool (decreases (rank t))
    (body (match t
      (case (leaf) true)
      (case (node v l r)
        (and (and (is_bst l) (is_bst r))
             (and (forall ((x int)) (=> (contains (view l) x) (< x v)))
                  (forall ((x int)) (=> (contains (view r) x) (> x v)))))))))
  (spec insert
    (params (t tree) (x i64))
    (returns (out tree))
    (requires (>= x 0) (is_bst t))
    (ensures (is_bst out) (== (view out) (union (view t) (iset-lit x))))
    (effects alloc))
  (def insert (decreases (rank t))
    (body
      (match t
        (case (leaf) (return (node x (leaf) (leaf))))
        (case (node v l r)
          (if (< x v)
            (block (let ((l2 tree)) (call insert l x)) (return (node v l2 r)))
            (if (> x v)
              (block (let ((r2 tree)) (call insert r x)) (return (node v l r2)))
              (return (node v l r)))))))))
```

What it shows:
- **A recursive data type.** `tree` contains itself, so its `node` fields are boxed in Rust, and building a `node` has effect `alloc` (§6).
- **`match` takes the tree apart.** In `insert` it moves `t`, so `v`, `l` and `r` are owned locals in that arm (§5).
- **`rank` proves termination.** `l` and `r` lie inside `t`, so their ranks are smaller (§9).
- **A ghost set.** `view` is the set of a tree's values.

## 2. Syntax

These productions extend §2's grammar.

```
item      = ... | data
data      = (data TNAME (TNAME*) ctor+)                ; type parameters, then constructors
ctor      = (NAME param*)                               ; a constructor and its fields
type      = ... | TNAME | (TNAME type+) | (tuple type type+) | (iset type) | (map type type)

stmt      = ... | (set-idx place e e) | (push place e)
          | (let NAME type (replace place e)) | (let-mut NAME type (replace place e))
          | (match e scase+)
          | (forall ((NAME type)+) (call NAME e*)) | (obtain ((NAME type)+) e)
place     = NAME | (idx place e) | (get place INT) | (field place NAME)
scase     = (case pat stmt)

e         = ... | (match e ecase+) | (is NAME e) | (field e NAME)
          | (tuple e e+) | (get e INT) | (rank e)
          | (iset-lit e*) | (iset-of ((NAME type)) e) | (map-lit (e e)*)
          | (union e e) | (diff e e) | (inter e e) | (update e e e) | (lookup e e)
ecase     = (case pat e)
pat       = (NAME NAME*) | (tuple NAME NAME+)           ; a constructor or a tuple, binding each field
```

`set-idx` and `push` now take a place where B17-0 took a NAME, and a NAME is a place, so every B17-0 statement still parses. A constructor call is written `(NAME e*)`, the same form as a ghost-fn call; the name tells them apart (§7).

**Canonical rules,** in addition to §2's:
- a `data` item lists its type parameters, as `()` when there are none, and its constructors in declaration order;
- `match` arms follow the scrutinee type's constructor order. Only the checker knows that order, so a misplaced arm is `E-TYPE-001` (§7), not `E-PARSE-001`;
- in `(get e K)` and `(get place K)`, K is a literal.

**Reserved words:** `data`, `case`, `match`, `is`, `field`, `tuple`, `get`, `replace`, `rank`, `iset`, `iset-lit`, `iset-of`, `map`, `map-lit`, `union`, `diff`, `inter`, `update`, `lookup` and `obtain` join §2's (D51). `forall` was already one. `replace` appears only as a `let` or `let-mut` initializer, so `(replace ...)` anywhere else is `E-PARSE-001`.

**Names (D82):**
- **Two namespaces.** Type names, the TNAMEs above, are data types and type parameters. Value names are everything §2 names: items, parameters, locals and binders. A name may be both, so a parameter `tree` of type `tree` is allowed.
- **Type names** are unique within a module, may not be a built-in type word (`bool`, `i64`, `int`, `vec`, `seq`, `multiset`, `ref`, `slice`, `tuple`, `iset`, `map`), and may not be a core library type (`option`, §9). A type parameter is in scope only in its `data` item, and may not reuse that item's other type names.
- **Constructor names** are value names, unique among the module's items and constructors under D41. So a single-constructor type may share its name with its constructor: `(data graph () (graph (adj (vec (vec i64)))))`.
- **Field names** are unique within one data type, across all its constructors, and may repeat across data types. A field is read with `field`, which looks it up in its operand's type.
- **Case binders** are locals of their arm. They follow D41: unique within the item, and visible only in their arm.

**Hashing (D92),** extending D45. The format stays version 0 (D46): every B17-0 item hashes as before, and these rules cover only B17-1's new forms.
- **A data item** has only a spec hash, covering the whole item, as a ghost-fn has. Its own name becomes `_`, its type parameters `$0`, `$1`, … in order, its constructors `#0`, `#1`, … in order, and its fields `.0`, `.1`, … in declaration order across all its constructors.
- **References to a data type,** in any item, become its spec hash: `D` is replaced by its hash, and `(D T ...)` by `(H T ...)`. A constructor C of D becomes `H#i`, for C D's i-th constructor, in constructor calls, `is` and patterns. A field F becomes `.k`, its index in its type, in `field` and in places. So editing a data type rehashes every spec that mentions it, and renaming a type, constructor or field changes no hash.
- **New binders:** case-pattern names, `iset-of` variables, and the binders of `forall` statements and `obtain` are numbered with D45's other binders, in the same walk.
- **Namespaces:** names resolve in their own namespace (D82), so a data type and a ghost-fn named alike are different items with different hashes.
- **One data type per hash:** two data items in a module with the same spec hash are `E-TYPE-002`, as two specs are. References by hash couldn't tell them apart.
- **The core library's `option`** hashes like any data item in it.

## 3. Types

| Type | Runtime? | Values |
|---|---|---|
| `(tuple T1 ... Tn)`, n ≥ 2 | when every Ti is | tuples of values of each Ti |
| a data type, `D` or `(D T1 ... Tn)` | when every field type is, after substitution | values built by D's constructors |
| `(vec T)` | yes, owned | finite sequences of `T`, for any runtime type T |
| `(ref (slice T))` | a parameter only | finite sequences of `T`, for any runtime type T; a spec's parameters only, and neither a runtime nor a ghost type |
| `(seq T)`, `(multiset T)` | ghost only | as in B17-0, for any well-formed T but a slice |
| `(iset T)` | ghost only | sets of `T`, finite or not, for any well-formed T but a slice |
| `(map K V)` | ghost only | finite maps from K to V, for any well-formed K and V but slices |

**Runtime and ghost types (D79, D83).** A type is a runtime type when it's `bool`, `i64`, or a vector, tuple or data type whose components are all runtime types. A slice is only ever a spec's parameter type (D69), and no other type contains one (`E-OWN-002`). Every other type is a ghost type. So `(option i64)` is a runtime type and `(option int)` a ghost one.

**Well-formed types (D83),** extending D68. Anything else is `E-TYPE-001`:
- a data type is applied to exactly as many types as it has parameters;
- a vector's element type is a runtime type;
- every data type has at least one finite value: a constructor whose every field type has one. `bool`, `i64` and `int` have one, and so does every vector, sequence, set, map and multiset, since it may be empty. A tuple has one when each component does, and a data type when one of its constructors does, found as a least fixed point over the module's types. So `(data loop () (more (next loop)))` is rejected;
- data types may contain themselves through fields, tuples, other data types and sequences, but never inside an `iset`, `map` or `multiset`, which the encoding represents as arrays (§9);
- two distinct data items may not contain each other (`E-TERM-002`, as for functions). Applying a declared type to another is not containment by it: `(option node)` inside `node` is `node` containing itself, since `option`'s own declaration doesn't mention `node`.

**Subtyping, in ghost context only (D83),** extending §3's rules:
- `(tuple T1 ... Tn) <: (tuple U1 ... Un)` when each Ti <: Ui;
- `(D T1 ... Tn) <: (D U1 ... Un)` when each Ti <: Ui for a covariant parameter, and Ti = Ui for the rest. A parameter is invariant when one of its occurrences in D's field types sits inside an `iset`, `map` or `multiset`, or is the argument for an invariant parameter of any data-type application, D's own recursive ones included, and covariant otherwise. The module's variances are the largest assignment that satisfies this, found by starting with every parameter covariant and marking invariant until nothing changes;
- `(iset T)` and `(map K V)`, like `(multiset T)`, have no subtyping rule (D70).

## 4. Runtime code and ghost code

In both contexts: constructor calls, `match`, `is`, `field`, `tuple` and `get`.

Ghost context only: `rank`, the set and map types and their operations, and quantifiers over the types §7 allows. In runtime code they are `E-GHOST-002`, as §4's ghost-only operations are.

A literal's type follows D70, extended to the new literals:
- **Destination first.** A set or map literal takes its element types from its destination when it has one, so `(iset-lit v)` with v an `i64` is an `(iset int)` where an `(iset int)` is expected. Sets and maps have no subtyping (§3), so without this the literal would be an `(iset i64)` and wouldn't fit. With no destination, its type joins its elements'.
- **Open types.** `(iset-lit)`, `(map-lit)` and a constructor call whose type parameter no argument fixes, such as `(none)`, take their open types from their destination. With none, an open element is `int` in ghost code and `i64` in runtime code. An element read from an open literal takes its destination's type, which may now be any type.
- **Operands.** In `union`, `diff`, `inter` and `==`, an operand that is a literal takes the other operand's type as its destination.

## 5. Ownership (tier 0)

§5's rules hold, with "vector" read as "moving value" wherever a rule moves or protects one.

1. **Copying and moving (D83).** `bool`, `i64` and slices are copied, as before. A tuple or data value is copied when every type inside it is copied and its type isn't recursive. Everything else moves: vectors, recursive data types, and anything holding them. So `(option i64)` is copied, and `(option tree)` moves.
2. **Where a moving value moves.** The owned positions are §5's, plus the value of `set-idx`, `push` or `replace`, the scrutinee of a runtime `match` statement, the body of a runtime `seq-build`, and the arguments of a constructor call or `tuple` that is itself in an owned position. A moving variable used whole in one of them moves. Moves happen only there (rule 7), so a statement's moves follow from its owned positions, left to right.
3. **Places (D84).** A place names a part of a value: a variable, an element `(idx p i)` of a vector, a component `(get p K)` of a tuple, or a field `(field p F)` of a data value.
   - **Reading:** reading a copied value through a place copies it. A moving value inside a place can only be read further, under `len`, `idx`, `get`, `field` or `is`, or viewed in ghost code. Using it whole in an owned position would move it out of its place, which is `E-OWN-007`.
   - **Updating:** `(set-idx p i e)` and `(push p e)` change a vector in place, and p's root must be a `let-mut` local (`E-OWN-003` otherwise). A slice is read-only and only ever a parameter, so a place rooted at one is `E-OWN-003` too.
   - **Taking out:** `(let x T (replace p e))` moves the value at p into x and leaves e in its place, as Rust's `std::mem::replace` does. p's root must be a `let-mut` local. This is the only way to move a value out of a place.
   - **The root outlives the value:** a statement's indices and value are evaluated first, and p's root must still be live after them (`E-OWN-001`). So `(push (field x kids) x)`, which would move x into itself, is rejected.
4. **`match` (D84).** In runtime code, a `match` statement's scrutinee is either a variable, which moves when its type moves, or an expression of a copied type. A `match` expression's scrutinee has a copied type, since an expression never moves anything (rule 7, `E-OWN-006`). A moving value inside a place is `E-OWN-007`: take it out with `replace` first. Each arm binds the fields as immutable runtime locals, which own what they hold. In ghost code, `match` reads its scrutinee and moves nothing.
5. **Branches and loops.** A `match` statement's arms join like an `if`'s: a variable moved in any arm that continues is moved afterwards. D76's loop rule covers every moving value. A runtime `seq-build`'s body runs once per element, so, like a loop body, it may not move a variable declared outside it (`E-OWN-004`).
6. **Each moving value in one argument.** §5's rule 7 (D72) covers every moving variable, in the arguments of a call, a constructor call or `tuple`, and in a return's expressions (`E-OWN-005`).
7. **Moving expressions (E-OWN-006, D84).** In runtime code, an expression of a moving type is a variable, `(vec-new)`, a runtime `seq-build`, a constructor call or `tuple`, or a call result. Any but a variable appears only as an owned position's whole value, or as an argument of a constructor or `tuple` that does. So a moving value never comes out of an `if` or `match` expression, is never read as a temporary, and no expression, loop condition included, moves anything.
8. **Borrows** are §5's: `(borrow NAME)` of a live vector, as a def-call argument. A slice of a vector of moving values gives read access to them through places, and none can move.

A data value can't be borrowed (§12), so a recursive read of a tree takes the tree. `bst_search`, whose spec returns only a `bool`, consumes its tree. A search that must keep its tree rebuilds it on the way out, which allocates.

## 6. Effects

- A constructor call has effect `alloc` when its constructor has a boxed field (D86): one whose type mentions the field's own data type other than inside a vector. In Rust that field is a `Box`. `node` in §1 has two. A trie node's `(vec (option trie))` field isn't boxed, since the vector already holds its elements on the heap.
- `tuple`, `match`, `is`, `field`, `get` and `replace` have no effect of their own.

## 7. Typing rules

**Items:**
- **Data:** `(data D (A1 ... Ak) (C1 fields1) ... (Cn fieldsn))` declares the type D with parameters A1 to Ak, and the constructors C1 to Cn. Each field type is a well-formed type over the Ai and the module's types. Field and constructor names follow §2.
- **Specs:** a spec's parameter and result types may be any runtime types (§3); a slice is still a parameter only. A ghost type there, or as the type of a runtime `let`, `let-mut` or call binding, is `E-GHOST-002`, as D68 says for B17-0's ghost types.

**Expressions:**
- **Construct:** `(C e1 ... en)` builds a value of C's data type. Each ei is checked against its field's type, with the type parameters inferred from the arguments and, failing that, from the destination (§4).
- **Match:** `(match e (case p1 x1) ... (case pn xn))`.
  - e's type is a data type or a tuple.
  - There is one arm per constructor, in the type's constructor order, and a tuple has one arm. A missing, repeated or misplaced arm is `E-TYPE-001`. There are no wildcards and no nested patterns.
  - A pattern `(C x1 ... xm)` names each of C's fields in order, and binds xi to field i's type with the type parameters substituted.
  - As an expression, every arm has the same type, which is the match's. Goals from an arm are assumed under the scrutinee being built by that arm's constructor.
  - As a statement, each arm is a statement, and the arms join as §5 says.
- **Is:** `(is C e)` is `bool`, for C a constructor of e's data type. Any other C is `E-TYPE-001`.
- **Field:** `(field e F)` has F's type, for F a field of e's data type, and any other F is `E-TYPE-001`. Unless every constructor of the type has F, it carries ⟦e was built by a constructor that has F⟧, the new goal family `FIELD` (§9).
- **Collections of any type:** `(vec-new)` and a runtime `seq-build` make vectors of any runtime type, and a ghost `seq-build` makes sequences of any type, so `(seq-build n (fn (i) (vec-new)))` builds a vector of empty vectors.
- **Tuple:** `(tuple e1 ... en)` is `(tuple T1 ... Tn)`. `(get e K)` is TK's type, for 0 ≤ K < n, and any other K is `E-TYPE-001`.
- **Rank:** `(rank e)` is `int`, for e of any data type, as D79 gives every data value a rank. On any other type it's `E-TYPE-001`.
- **Sets:**
  - `(iset-lit e1 ... en)` is an `(iset T)`, the finite set of the ei, each a T.
  - `(iset-of ((x T)) e)` is an `(iset T)`: every x of type T for which the `bool` e holds. Its binder follows the quantifier rules below.
  - `(union s t)`, `(diff s t)` and `(inter s t)` take two `(iset T)` and give one.
  - `(contains s x)` is `bool`, for s an `(iset T)` and x a T. It's B17-0's `contains`, which now also takes sets and maps.
- **Maps:**
  - `(map-lit (k1 v1) ... (kn vn))` is a `(map K V)`, from each ki, a K, to its vi, a V. A later entry replaces an earlier one with the same key.
  - `(update m k v)` is a `(map K V)`, for m a `(map K V)`, k a K and v a V: m with k mapped to v.
  - `(lookup m k)` is a V, k's value, with ⟦contains m k⟧, a ghost `BOUNDS` goal.
  - `(contains m k)` is `bool`: whether k is a key.
  - `(union m n)` takes two `(map K V)` and gives one, with the keys of both and n's value where both have the key.
- **Quantifiers (D90):** a binder of `forall`, `exists` or `iset-of` has an exact type, and any other binder is `E-TYPE-001`. `bool` and `int` are exact. A `seq`, `iset` or tuple is exact when its parts are. A data type is exact when every field type of every constructor is, after substitution. Its own recursive occurrences count as exact, except one reached through a `seq`: D61's sequences are uninterpreted, so the encoding would admit a cyclic value such as `x = (more (seq-lit x))`. So `i64`, a vector, a slice, a `multiset` or a `map` anywhere inside makes a type inexact, even inside a data type's fields: `(data d () (c (x i64)))` is not exact. The encoding (§9) represents exactly the values of the allowed types. It would admit values outside the others, such as an infinite map or `(some 2^63)`, so an `exists` could be proved with no real witness. D68's `i64` binder rule is the same rule for B17-0's types.
- **Equality:** `==` and `!=` compare any two values of joinable types in ghost code, extensionally: sequences by length and elements, multisets by counts, sets by members, maps by keys and values, and tuples and data values field by field. In runtime code they still compare only `bool` and `i64`, and comparing anything else there is `E-GHOST-002`, as for collections (D71).
- **Literals and open types:** see §4.

**Statements:**
- **Match:** as above.
- **Set-idx and push:** as §7, with a place where B17-0 had a variable, and ⟦0 ≤ i < len⟧ for each `idx` the place passes through, plus ⟦FIELD⟧ for each `field`.
- **Replace:** `(let x T (replace p e))` needs p to be a place of type T rooted at a `let-mut` local, and e to be a T. x gets p's old value, and p gets e. `let-mut` makes x mutable. It carries the same goals as `set-idx`: ⟦0 ≤ i < len⟧ for each `idx` p passes through, and ⟦FIELD⟧ for each `field`.
- **Forall (D99):** `(forall ((x T) ...) (call L e*))` applies the lemma L at every value of its binders.
  - **Checking:** L is a lemma, and anything else is `E-TYPE-001`, a name of the wrong kind. Each binder has an exact type (above), scoped to the statement. The arguments are checked in ghost context against L's parameter types, as for a lemma call.
  - **Goals:** each argument's own goals, as ⟦∀x. goal⟧. L's `requires` isn't a goal here, so a proof passes the binders and lets L's `requires` guard them: `(forall ((i int)) (call l s i))`, not `(call l (idx s i))`. Inside L's own body, ⟦∀x. requires ⇒ 0 ≤ callee measure < caller measure⟧, under the path's assumptions.
  - **The fact:** from the statement on, along its path, ∀x. ⟦requires⟧ ⇒ ⟦ensures⟧, with each of L's clause lists conjoined and the arguments substituted without capture.
- **Obtain (D100):** `(obtain ((x T) ...) e)`, for a `bool` e, has the goal ⟦∃x. e⟧, and then binds each x as an immutable ghost local, with e assumed.
  - **Binders:** each has an exact type (above). They are locals under D41, visible to the end of the enclosing block, loop body or branch.
  - **Goals:** e's own goals, under the binders, then ⟦∃x. e⟧.
- **Both** are ghost statements, with no effects, that move nothing. They may appear wherever a lemma call may: in def bodies, and in lemma bodies, whose list of allowed statements (§7) they join. A witness is a ghost local, so it never reaches a runtime value (`E-GHOST-001`).

## 8. Dynamic semantics

**Values,** in addition to §8's: tuples of values; data values `C(v1, ..., vn)`; and sequences of any values. In ghost code, also finite multisets, sets, which may be infinite, and finite maps. Ownership still constrains only which names may be used.

**`err`** gains one case: reading a field that the value's constructor lacks, in runtime code. In ghost code with checking on, that and a map lookup outside the map are contract outcomes, `FIELD` and `BOUNDS`, as a ghost index out of range is (D57).

**Operations:**
- **Places:** an update through a place builds the new root value with that one part replaced, so the semantics stays value-based. Rust performs the same update in place.
- **`match`** selects the arm for the scrutinee's constructor and binds its fields.
- **`rank`** is a data value's height (D87): 0 for a value with no data value inside it, and otherwise one more than the greatest rank among the data values directly inside it. Those are the ones its fields reach through tuple components and sequence elements, without passing through another data value.

**Checking (D57, D58):** with checking on, the interpreter evaluates the new ghost expressions as well.
- **Finite sets and maps** are evaluated as values.
- **A set built by `iset-of`** is kept as its predicate: membership evaluates the body at the member, and equality with such a set is unknown.
- **A quantifier's binder** may also be bounded by membership: a leading conjunct `(contains E x)`, with E a finite set, a sequence or a map, ranges x over E's members or keys, for x of any type but `bool` (D102). A quantifier over a type B17-1 adds is otherwise unknown, since no range can be read off its guard (D58).
- **`forall` statements** check nothing, as a lemma call doesn't. **`obtain`** finds no witness, so its locals are unknown, and so is any ghost code that reads them (D58).

**Interface 10** gains these values and the `FIELD` reason for `err`.

## 9. Proof goals

| Family | Goal |
|---|---|
| `E-PROOF-FIELD` | A field read's value was built by a constructor that has the field |

`E-PROOF-BOUNDS` also covers a map lookup, and the index of each `idx` a place passes through in `set-idx`, `push` and `replace`.

A `forall` statement's argument goals keep their families, quantified over its binders, and its measure goal is `E-PROOF-TERM`. An `obtain`'s ⟦∃x. e⟧ is `E-PROOF-ASSERT`.

**Encoding, interface 11 version 0.2 (D89):**
- **Tuples and data types** are SMT-LIB datatypes, with Z3's parametric datatypes for type parameters. A constructor test is the datatype's tester, and a field read is its selector, guarded by the `FIELD` goal.
- **Sequences** keep D61's encoding: one uninterpreted sort per element sort, with §9's background facts instantiated for each element sort a query uses.
- **Multisets** are count arrays over any element sort.
- **Sets** are arrays to `Bool`. A literal is built by stores, `iset-of` is a lambda, and `union`, `diff` and `inter` are array maps.
- **Maps** are arrays from keys to `(option V)`, with `none` outside the map, so array equality is map equality.
- **Equality** is extensional at every type (§7). Sets, maps and multisets get that from array extensionality, and tuples and data from datatype equality once their fields compare. Sequences, and anything holding them, are compared through an equality predicate per sort, defined by length and elements, which implies SMT equality. Dafny's `Seq#Equal` works the same way.
- **`rank`** is an uninterpreted function to `Int` per data sort, with these axioms:
  - every rank is at least 0;
  - for each constructor, and each path from one of its fields through tuple components and sequence elements to a data value, that value has a smaller rank than the one the constructor builds.

  Each path stops at the first data value it reaches, so there are finitely many, and chained, they reach every data value inside another. Height (§8) satisfies every axiom, so the encoding agrees with the interpreter.
- **`match` and `is`:** in each arm, the scrutinee equals its constructor applied to fresh field values, which are the arm's binders.

**The core library** gains `(data option (t) (none) (some (value t)))`, so a port need not declare its own. `option`, `none` and `some` are reserved, as §9's names are. No suite program or core law uses them. `value` is a field name, and field names are per type (§2). Sets and maps get no laws beyond their encoding, since array theory decides their operations.

**Tier 0 errors** gain one code. The other new conditions reuse §9's codes, as the sections above say.

| Code | Error |
|---|---|
| `E-OWN-007` | A moving value moved out of a place: as a whole value in an owned position, or as a runtime `match`'s scrutinee |

## 10. Verification levels

D80 defines them. This section fixes what D80 left to the spec text.

- **Declaring:** `b17c verify --level L0|L1|L2|L3 FILE` fails unless the module reaches that level. Its manifest (interface 4) will take over the declaration.
- **The report** (interface 5, D63) gains:
  - the level reached;
  - each tested goal with the number of inputs that evaluated it;
  - each goal neither proved nor tested;
  - for L2, the goals whose proofs didn't count because they rested on goals that aren't proved.
- **Ghost-fns in L2's closure (D91):** a goal's canonical query includes the defining equations of the ghost-fns it uses (D63), and a proof may rest on any of them. So it counts for L2 only once every goal of each such ghost-fn counts too: the well-definedness of its `requires`, its measure and its body, and its termination, and likewise for the ghost-fns those goals' queries include. WP5 solves a goal again without an equation that doesn't count. This adds to D80's list of what a proof may assume.
- **Property tests (D88):**
  - **Seed:** `state` starts at the first 16 hex digits after `spec0:` in the def's spec hash (D46), read as an unsigned 64-bit integer, most significant digit first. Inputs therefore change when the spec changes, and never when only the body does. All arithmetic is on unsigned 64-bit integers, and `>>` is a logical shift.
  - **Counts:** 100 inputs that satisfy the `requires`, from at most 10,000 draws. A draw whose `requires` is unknown is dropped, as one whose `requires` fails is.
  - **A draw** gives each parameter a value in declaration order, at depth 0, from one stream:

```
next()          state ← state + 0x9E3779B97F4A7C15                       (all mod 2^64)
                z ← (state ⊕ (state >> 30)) × 0xBF58476D1CE4E5B9
                z ← (z ⊕ (z >> 27)) × 0x94D049BB133111EB
                return z ⊕ (z >> 31)                                    (SplitMix64)
below(n)        next() mod n
bool            below(2) = 1
i64             k ← below(4)
                k = 0 or 1: below(21) − 10
                k = 2: the below(7)th of −2^63, −2^63 + 1, −1, 0, 1, 2^63 − 2, 2^63 − 1
                k = 3: next() read as a two's complement i64
vector, slice   n ← below(9), then n elements in order, at the same depth
tuple           its components in order, at the same depth
data at depth d d = 4: the type's smallest value
                otherwise: the below(k)th of its k constructors, then its fields in order, at depth d + 1
smallest value  false, 0, the empty vector, a tuple of smallest values; for a data type, the value built
                with the fewest constructors in all, from the first constructor in declaration order
                among ties, with the smallest value for each field
```

  §3 guarantees every data type a smallest value.

## 11. How a task is posed

§10's rules hold. Porting AlgoVeri adds these:
- **Option:** Dafny's `Option<T>` becomes the core library's `option`, and a method on it, such as `is_some`, becomes `is`.
- **Naturals:** `nat` becomes `int` or `i64`, with a `requires` that it's at least 0 (D42).
- **Characters:** they become `i64`, as AlgoVeri's own tries store them.
- **Infinite sets:** `iset` comprehensions become `iset-of`.
- **Methods inside a datatype** become top-level ghost-fns taking the value as their first parameter.
- **Cardinality:** `max_matching`, the one task that counts a set's elements, states its matching as a sequence of distinct edges (D79).
- **Flows:** `edmond_karp` and `push_relabel` quantify over every flow, which Dafny states as a map. A binder can't be a map (§7, D90), so their ports state a flow as a sequence of sequences of `int`, indexed by the two vertices.

## 12. Left out of B17-1

| Feature | Comes back with | Why it's out |
|---|---|---|
| Generic functions, specs and lemmas | Later | No surveyed task needs one (D79) |
| Set cardinality | Later | One task needs it, and a sequence states it as well (D79) |
| Quantifying over `i64`, vectors, multisets or maps | When the encoding states their values exactly | The encoding would admit values outside them (§7, D90). Ports quantify over `int` and `seq` instead |
| Runtime sets and maps | Later | The solutions use vertex-indexed vectors (D79) |
| Strings and characters, floats | Later | §11 |
| Borrowing a data value, `&mut` | Later | Places cover the surveyed tasks without lifetimes. Until then, a recursive read of a tree consumes it, or rebuilds it at the cost of allocation (§5) |
| Mutual recursion, of functions or data types | With group hashing (D22) | §11 |
| Vector capacity | With allocation bounds (D30) | §11 |
| Data-type invariants, refinement links | When a task needs an invariant across a module's operations | D79 |

## 13. Accept/reject suite

The suite extends `suite/` and keeps its layout, with B17-1's programs in `suite/b17-1/`.

**Accept:** a port of each feature's smallest AlgoVeri task that verifies end to end:
- `bst_insert` (§1) and `bst_search`: data types, `match`, `rank`;
- `lca`: `option`;
- `trie_insert`: a vector of optional nodes, places and `replace`;
- `bfs`: a graph record, nested vectors and a path quantifier;
- `kruskal`: tuples in a vector;
- `longest_palindrome_substring`: a tuple result;
- `discrete_logarithm`: an optional result;
- `segmenttree_query`: ghost maps;
- `coin_change`: a quantifier over sequences.

**Reject:** at least one program per new rule, each labelled with its code. Examples:
- a missing or misplaced `match` arm;
- a type with no finite value;
- two mutually recursive data types;
- a slice inside a tuple;
- moving a vector out of a vector of vectors;
- matching a moving field without `replace`;
- `replace` outside a `let`;
- a node built without `alloc`;
- `rank` of a tuple;
- an `i64` set binder;
- a binder of type `(map int int)`, one of type `(option i64)`, and one of a data type with an `i64` field;
- two data types identical up to names (`E-TYPE-002`);
- a data type that contains itself inside an `iset`;
- a `seq-build` whose body moves an outer vector;
- `(push (field x kids) x)`, which moves its own root;
- a constructor with a moving argument inside an `if` expression;
- a field read on the wrong constructor (`E-PROOF-FIELD`);
- a map lookup outside the map, and a `replace` at an index out of range (`E-PROOF-BOUNDS`).

WP3's checker must agree with every tier 0 label, and WP5's verifier with every proof label, as for B17-0 (D44).

## 14. Decisions

These are D81–D92, D99, D100 and D102 in `DECISIONS.md`, all accepted: D102 on 2026-10-29, the others on 2026-10-28.

- **D81:** the syntax of data types, constructor calls, `match`, `is`, `field`, `tuple` and `get` (§2, §7). `match` names every constructor once, in declaration order, with no wildcards or nested patterns.
- **D82:** types and values have separate namespaces. Constructors are value names, and field names are per data type (§2).
- **D83:** runtime types, copying, well-formed data types, and ghost subtyping by each parameter's variance (§3, §5).
- **D84:** places, `replace`, `match`'s scrutinee rule and `E-OWN-007`; moves only in owned positions; a `seq-build` body moves nothing outer; a mutated place's root outlives its value (§5).
- **D85:** the names and operations of ghost sets and maps (§2, §7).
- **D86:** a constructor with a boxed field has effect `alloc` (§6).
- **D87:** `rank` is height, on every data value (§7, §8).
- **D88:** the property-test generator, its stream and its counts (§10).
- **D89:** interface 11 version 0.2: the encoding of tuples, data, sets, maps, equality and `rank` (§9).
- **D90:** which types a quantifier may bind, and the flow ports that follow from it (§7, §11).
- **D91:** L2's closure covers the ghost-fns a proof unfolds (§10). It refines D80.
- **D92:** how data items and the new binders are hashed (§2). It refines D45.
- **D99:** the `forall` statement, which applies a lemma at every value of its binders (§7, §9).
- **D100:** the `obtain` statement, which proves an ∃ and names its witness (§7, §9).
- **D102:** membership in a finite collection bounds a quantifier's binder when the interpreter checks a run (§8). It extends D58.
