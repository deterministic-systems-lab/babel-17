# B17-0: core semantics (WP1a)

**Status:** Frozen on 2026-10-28, at version 1.0. This document defines interface 6 (core terms, D27) and the B17-0 part of interface 1 (the grammar). It froze together with the accept/reject suite in `suite/` (§12) once WP3's checker agreed with every tier 0 label in the suite (D44), and that completed WP1a. Changing it now takes a new decision.

**Implements:**
- D20, the subset;
- D16, WP1a's scope;
- D17, D18, D22 and D23, which constrain it;
- D29 and D30, which amend the worked example;
- D45, which hashes canonical bytes (§2) and rejects duplicate specs (§9);
- D47–D55, which settle §2's canonical layout and reading rules;
- D60 and D61, which restate §10's porting rule and §9's encoding;
- D66–D78, WP3's readings of §2–§9, which settle what the text left open.

**Its own decisions:** the choices this document makes beyond the earlier log are collected in §13 as D33–D43, all accepted.

B17-0 is the smallest Babel-17 that can express the seed tasks and the corrected worked example. Three ideas shape it:
- **Value semantics.** Every value a program can see is a plain value. The verifier encodes vectors as sequences, with no heap model, which is the encoding gain D17 is after.
- **Ownership without lifetimes.** Vectors are owned and move. Slices are shared borrows that can't escape the call they're passed to. `rustc` can re-check all of this when Phase 1 emits Rust (D18).
- **No runtime error the verifier hasn't ruled out.** Overflow, out-of-bounds indexing and division by zero are all proof goals. A verified B17-0 program can only stop early through an explicit `panic` or a failed allocation.

## 1. A program

The worked example (D29), in B17-0's canonical form. The person signs the `spec`; the agent writes only the `def`.

```
(module sorted_merge
  (header
    (purpose "Combine two ordered sequences into one, keeping duplicates.")
    (invariants "The output is ordered; no element is gained or lost.")
    (failures "None for sorted input. Allocation failure aborts."))
  (spec merge_sorted
    (params (a (ref (slice i64))) (b (ref (slice i64))))
    (returns (out (vec i64)))
    (requires (sorted a) (sorted b) (<= (+ (len a) (len b)) 9223372036854775807))
    (ensures (sorted out) (== (multiset out) (msum (multiset a) (multiset b))))
    (effects alloc))
  (def merge_sorted
    (body
      (let-mut out (vec i64) (vec-new))
      (let-mut i i64 0)
      (let-mut j i64 0)
      (while (or (< i (len a)) (< j (len b)))
        (invariant (and (and (<= 0 i) (<= i (len a))) (and (<= 0 j) (<= j (len b)))))
        (invariant (sorted out))
        (invariant (== (multiset out) (msum (multiset (take a i)) (multiset (take b j)))))
        (invariant (=> (and (> (len out) 0) (< i (len a))) (<= (last out) (idx a i))))
        (invariant (=> (and (> (len out) 0) (< j (len b))) (<= (last out) (idx b j))))
        (decreases (- (+ (len a) (len b)) (+ i j)))
        (if (or (== j (len b)) (and (< i (len a)) (<= (idx a i) (idx b j))))
          (block (push out (idx a i)) (set i (+ i 1)))
          (block (push out (idx b j)) (set j (+ j 1)))))
      (return out))))
```

`sorted` comes from the core library (§9), which is in scope in every module.

Compared with the spec's original sketch:
- **No type parameter.** D20 restricts B17-0 to integers.
- **No capacity.** D35 explains why.
- **No `effects` on the `def`.** Its effects are checked against the spec's.
- **Statement sequences use `block`,** not `seq`, which names the sequence type.

## 2. Syntax

The canonical form is an S-expression. In B17-0 it is also the core language: there is no separate surface syntax to elaborate (D33). This section is the B17-0 part of interface 1 (the grammar, WP2) and interface 6 (core terms, WP1a). Productions below use `*` for zero or more and `?` for optional.

```
module    = (module NAME header item*)
header    = (header (purpose STR) (invariants STR) (failures STR))
item      = ghost-fn | lemma | spec | def
ghost-fn  = (ghost-fn NAME (param*) type (requires e)* (decreases e)? (body e))
lemma     = (lemma NAME (params param*) (requires e*)? (ensures e*)? (decreases e)? (body stmt*))
spec      = (spec NAME (params param*) (returns param*) (requires e*)? (ensures e*)? (effects EFF*))
def       = (def NAME (decreases e)? (body stmt*))
param     = (NAME type)
type      = bool | i64 | int | (seq type) | (multiset type) | (vec type) | (ref (slice type))
EFF       = alloc | panic | io

stmt      = (let NAME type e) | (let-mut NAME type e) | (set NAME e) | (set-idx NAME e e)
          | (push NAME e) | (if e stmt stmt) | (block stmt*) | (while e inv* dec stmt*)
          | (call NAME e*) | (let (param+) (call NAME e*)) | (let-mut (param+) (call NAME e*))
          | (assert e) | (ghost-let NAME type e) | (ghost-let-mut NAME type e) | (ghost-set NAME e)
          | (return e*) | (panic STR) | (print e)
inv       = (invariant e)
dec       = (decreases e)

e         = INT | true | false | NAME | (OP e e) | (not e) | (neg e) | (if e e e)
          | (len e) | (idx e e) | (borrow NAME) | (vec-new) | (seq-build e (fn (NAME) e))
          | (NAME e*)                                   ; ghost-fn call
          | (forall ((NAME type)+) e) | (exists ((NAME type)+) e)
          | (seq-lit e*) | (take e e) | (drop e e) | (concat e e) | (last e) | (contains e e)
          | (multiset e) | (msum e e) | (occurrences e e)
OP        = + | - | * | / | % | == | != | < | <= | > | >= | and | or | =>
```

**Canonical rules:**
- single spaces, and no trailing whitespace;
- **layout (D47):**
  - the first line is `(module NAME (header ...)`;
  - each item follows on its own line, unindented and in source order;
  - the module's closing paren ends the last line, and no newline follows it;
- children in grammar order, and each effect at most once, in the order `alloc`, `panic`, `io` (D52);
- integers are signed decimal literals with no leading zeros, no `+` and no `-0`, such as `-1`, so `i64::MIN` is `-9223372036854775808`; `(neg INT)` is not canonical;
- strings in UTF-8 with `\"` and `\\` as the only escapes;
- an optional `(requires)` or `(ensures)` is left out, never left empty (D54).

The pretty layout above is a projection. Canonical bytes put each item on one line, and D45 hashes them after replacing names.

**Reading:** a program parses only if it is canonical bytes laid out with different whitespace, so canonicalizing only ever changes whitespace. Anything else is `E-PARSE-001`:
- **Whitespace:** space, tab, line feed and carriage return are the only whitespace, and adjacent list elements need at least one between them (D48, D49).
- **Comments:** there are none. `;` in the grammar above is notation (D48).
- **Strings:** they hold no control characters (U+0000–U+001F, U+007F) and aren't Unicode-normalized (D50).
- **Non-canonical forms:** non-canonical integers, `(neg INT)` and empty optional clauses don't parse (D53, D54).
- **Integer size:** a literal's size isn't checked while parsing, since ghost integers are unbounded. WP3 checks that it fits its type.
- **Nesting:** lists nest at most 128 deep, counting the module (D55).

Diagnostics give 1-based lines and columns, counting code points (D48).

**Names:**
- A name matches `[a-z][a-z0-9_]*`.
- Every word of the grammar above, from `module` to `occurrences`, is reserved, and using one as a name is `E-PARSE-001` (D51). The core library's names (§9) are reserved too, but they parse as names, so declaring one is `E-TYPE-002`.
- Item names are unique within a module, with one exception: a `spec` and the `def` that implements it share a name and together form one definition.
- Parameter and local names are unique within their item, and none may reuse an item name, so there is no shadowing (D41). That holds even for locals in separate blocks.
- A local is visible from its declaration to the end of the innermost `block`, loop body or `if` branch that declares it. A branch is a single statement, so a `let` that forms a whole branch is visible nowhere after it. A use outside that range is `E-TYPE-002`, as for any undefined name (D66).
- Result names are in scope only in `ensures`, so a `def` may give a local its result's name, as §1 does with `out`. A result may not share a name with a parameter or another result (D66).
- A binder of `forall`, `exists` or `fn` is scoped to its body. It may not reuse a name in scope where it appears: a parameter, a result (inside `ensures`), a local, an item or an enclosing binder. Separate binders may share a name.
- Items may refer to one another in any order within a module.

## 3. Types

| Type | Runtime? | Values |
|---|---|---|
| `bool` | yes | `true`, `false` |
| `i64` | yes | integers in [-2^63, 2^63) |
| `int` | ghost only | all integers |
| `(vec T)` | yes, owned | finite sequences of `T`; `T` is `bool` or `i64` |
| `(ref (slice T))` | yes, shared borrow | finite sequences of `T`; `T` is `bool` or `i64`; a spec's parameters only (§5) |
| `(seq T)` | ghost only | finite sequences of `T`; `T` is `bool`, `i64` or `int` |
| `(multiset T)` | ghost only | finite multisets of `T`; `T` is `bool`, `i64` or `int` |

Collections never nest (§11). Any other type is `E-TYPE-001` (D68).

**Subtyping, in ghost context only:**
- `i64 <: int`.
- `(vec T) <: (seq T)` and `(ref (slice T)) <: (seq T)`: a collection is viewed as its value.
- `(seq T) <: (seq U)` when `T <: U`.

There are no other rules. In particular `(multiset T)` has none, so `(multiset i64)` and `(multiset int)` don't compare (D70). In runtime code there is no subtyping and no implicit conversion (D34).

## 4. Runtime code and ghost code

Every expression is checked in one of two contexts.

**Ghost context** covers contracts, invariants, `decreases`, `assert`, ghost locals, and the bodies of `ghost-fn`s and `lemma`s. In it:
- arithmetic is on `int` and can't overflow;
- quantifiers, `seq`, `multiset` and the sequence operations are allowed;
- calls to `ghost-fn`s are allowed;
- `def`s, `push` and other effects are not.

**Runtime context** covers everything else in a `def` body. In it:
- arithmetic is on `i64`, with an overflow goal;
- ghost types and ghost-only operations are rejected (`E-GHOST-*`). `int`, `(seq T)` and `(multiset T)` are `E-GHOST-002` as a spec's parameter or result type, or as the type of a `let`, `let-mut` or call result binding (D68);
- a ghost local may never flow into a runtime value.

A literal takes its type from its context (D70):
- in runtime context it's an `i64` and must fit in one (`E-TYPE-001`, D53);
- in ghost context it's an `int` of any size, unless its destination is `i64`, where it must fit.

## 5. Ownership (tier 0)

These rules give data-race and aliasing freedom without lifetimes (D36). Error codes are in parentheses.

1. **Copying and moving.** `bool`, `i64` and `(ref (slice T))` values are copied. `(vec T)` values move.
2. **Where a vector moves.** A vector variable moves when it's used as a whole value in an owned position: a `let` or `let-mut` initializer, the right side of `set`, an owned call argument, or `return`. Using it under `len`, `idx`, `borrow` or anywhere in ghost context reads it without moving.
3. **Use after move.** A moved variable can't be used in runtime context until `set` gives it a new value (`E-OWN-001`). In ghost context, a moved parameter still denotes its value at entry, so `ensures` and invariants can mention a vector the body has moved.
4. **Slices are read-only.** `(borrow v)` makes a `(ref (slice T))` from a live vector (`E-OWN-001`, or `E-TYPE-001` if v isn't a vector). It may appear only as an argument of a `def` call, for a slice parameter. Anywhere else, including a lemma call's arguments and ghost code, is `E-OWN-002`. Only a spec's parameters may have a slice type, so slices can't be stored, returned, put in a local, or taken by a ghost-fn or lemma (`E-OWN-002`, D69). A borrow therefore never outlives the call, and no lifetime is ever needed. Ghost code views a vector as a `(seq T)` without one (§3).
5. **Mutation.** Only `let-mut` locals can be changed with `set`, `set-idx` or `push`, and only `ghost-let-mut` locals with `ghost-set`. Changing a parameter, a `let` or a `ghost-let` is `E-OWN-003`. Changing a binding of the other kind, a ghost local with `set` or a runtime one with `ghost-set`, is `E-GHOST-001` (D75). To change an owned vector parameter, move it into a `let-mut` local.
6. **Branches and loops.** Only paths that continue normally are joined; paths that end in `return` or `panic` don't reach the join.
   - A variable moved on either continuing branch of an `if` counts as moved afterwards.
   - The normally continuing end of a loop body must leave every outer variable in the state it found it (`E-OWN-004`). That rules out both directions: an outer vector live at the start can't end moved, and one moved before the loop can't end live because a `set` gave it a value. Vectors the body declares aren't outer (D76).
7. **Each vector in at most one argument.** A vector variable may appear in at most one of a call's arguments, and in at most one of a return's expressions, however it appears: owned, borrowed, or only read, as in `(len v)` (`E-OWN-005`). So `(call g (borrow v) (len v))` and `(return v (len v))` are rejected; a program binds `(len v)` first, as Rust requires. Several appearances inside one argument count as one, and lemma calls are ghost, so they aren't counted (D72). Arguments are evaluated left to right.

An in-place algorithm takes its vector by value and returns it:
```
(spec reverse_in_place
  (params (a (vec i64)))
  (returns (r (vec i64)))
  (ensures (== (len r) (len a))
           (forall ((i int)) (=> (and (<= 0 i) (< i (len a))) (== (idx r i) (idx a (- (- (len a) 1) i))))))
  (effects))
```
Rust compiles this to an in-place update. The verifier sees two sequence values and no heap, so no `old` is needed.

## 6. Effects

- `vec-new` has no effect.
- `push` and a runtime `seq-build` have effect `alloc`.
- `(panic STR)` has effect `panic`.
- `(print e)`, with e an `i64`, has effect `io`.
- A call has the effects its callee's spec declares.

A statement's effects are the union of its own effect and the effects of every expression and statement inside it. A `def` body's effects must be a subset of its spec's `effects` (`E-EFF-001`). `ghost-fn`s and `lemma`s have no effects. An effect says what a function may do, not how much (D20). Allocation amounts are bounds under D30.

`panic` ends execution abnormally, and `ensures` constrain only normal returns. A spec that leaves `panic` out of its effects guarantees the function never panics. Allocation failure aborts the process and is outside the semantics (D29).

## 7. Typing rules

Notation:
- `Γ ⊢g e : T` means e has type T in ghost context.
- `Γ ⊢r e : T ! ε` means e has type T in runtime context, with effect set ε.
- `Γ ⊢ s ⊣ Γ' ! ε` means statement s takes context Γ to Γ' with effects ε. Γ maps names to a type, mutability (mutable or not), kind (ghost or runtime) and move state (live or moved). Γ' is `⊥` when no path through s continues normally, because every path ends in `return` or `panic`; joins ignore `⊥`.

Goals that a rule generates are written `⟦goal⟧` and discharged by the verifier (§9).

**Expressions:**
- **Var-R:** if x has type T, is live and is a runtime binding, then Γ ⊢r `x : T ! ∅`. A ghost binding is never usable in runtime context, including inside conditions and `seq-build` bodies (`E-GHOST-001`).
- **Var-G:** any binding, live or moved, can be read in ghost context.
- **Sub:** in ghost context only, Γ ⊢g e : T and T <: U ⊢ e : U.
- **Arith-R:** for `op` ∈ {+, -, *}, if a and b are `i64` (with effects ε_a and ε_b) then `(op a b)` is `i64 ! ε_a ∪ ε_b`, with ⟦result in i64⟧. For `/` and `%`: ⟦b ≠ 0⟧ and ⟦not (a = −2^63 and b = −1)⟧, because Rust panics on both, even for `%`, whose mathematical result is 0.
- **Neg-R:** `(neg a)` is `i64` with ⟦a ≠ −2^63⟧. **Neg-G:** `(neg a)` on `int`, with no goal.
- **Arith-G:** the same operators on `int`, with only ⟦b ≠ 0⟧ for `/` and `%`. Division truncates toward zero in both contexts, as Rust's does (D37). Ghost arithmetic and `neg` produce `int`, which isn't an `i64`, so `(ghost-let g i64 (+ x 1))` is `E-TYPE-001` (D70).
- **Cmp:** `<`, `<=`, `>`, `>=` on integers. `==` and `!=` on `bool` or integers in either context, and on collections and multisets in ghost context only; in runtime code that's `E-GHOST-002` (D71). The result is `bool`.
- **Logic:**
  - `and`, `or` and `=>` evaluate their right operand only when the left one hasn't already decided the result.
  - Goals from the right operand are assumed under the left being true (for `and`, `=>`) or false (for `or`).
  - `not` takes a `bool`.
- **If-e:** `(if c a b)`, where c is `bool` and a and b have the same type. Goals from a are assumed under c, and goals from b under not c.
- **Vec-new:** `(vec-new)` is the empty `(vec T)`, with T taken from where it's used: the declared type of a `let`, the target of `set`, a declared result, or a parameter.
- **Runtime vector expressions:** in runtime context, a `(vec T)`-typed expression must be a variable, `(vec-new)`, a runtime `seq-build`, or a call result. A vector can never come out of an `if` expression, so moving a variable is the only way to transfer one, and two live names can't share a vector (`E-OWN-006`).
- **Len:** `(len s)` is `i64` in runtime context and `int` in ghost context, for s a vector, slice or (in ghost) seq. `len`, `idx`, `take`, `drop`, `last`, `contains` and `occurrences` take sequences, never multisets (D70).
- **Idx:** `(idx s i)` is the element type, with ⟦0 ≤ i < len s⟧.
- **Seq-build:** `(seq-build n (fn (i) e))`.
  - In runtime context: n is `i64`, ⟦n ≥ 0⟧, e has type T ∈ {`bool`, `i64`}, and the result is `(vec T)` with effect `alloc`.
  - In ghost context: n is `int`, ⟦n ≥ 0⟧, and the result is `(seq T)`.
  - In both: e is checked with `i` bound, and with 0 ≤ i < n assumed. That makes `(seq-build (len a) (fn (i) (idx a (- (- (len a) 1) i))))` correct as written. This is the friction WP17 measured in Dafny (D38).
  - The result r satisfies `len r = n` and, for every 0 ≤ i < n, `idx r i = e[i]`. The verifier states exactly these two facts.
- **Ghost-only expressions:**
  - `(forall ((x T) ...) e)` and `(exists ...)` bind `int` or `bool` variables over a `bool` body. An `i64` binder is `E-TYPE-001` (D68).
  - `(seq-lit e1 ... en)` is a `(seq T)` of n elements; an empty one takes T from where it's used.
  - **Open element types (D70):** an empty `seq-lit`, or a `(vec-new)` whose context fixes no element type, is never an error on its own. An element read from one, by `idx` or `last`, takes its destination's type, which can't be a collection. With no destination, it's `int` in ghost code and `i64` in runtime code.
  - `(take s k)` and `(drop s k)` carry ⟦0 ≤ k ≤ len s⟧. `(last s)` carries ⟦len s > 0⟧. `(concat s t)` has no goal.
  - `(contains s x)` is `bool`. `(occurrences s x)` is the `int` count of x in s.
  - `(multiset s)` is a `(multiset T)`, and `(msum m n)` is multiset union with multiplicities added.
  - A ghost-fn call carries ⟦the callee's requires⟧.

**Statements:**
- **Let:** if e is `T ! ε` and x is new, then `(let x T e)` adds x (immutable, runtime, live) with effects ε. `let-mut` is the same but mutable. A vector-typed e that is a variable moves it.
- **Set:**
  - `(set x e)` needs x to be a mutable runtime local of type T, and e to be `T` in runtime context. It makes x live again.
  - `(set-idx v i e)` needs v to be a live, mutable `(vec T)`, i to be `i64` and e to be `T`, with ⟦0 ≤ i < len v⟧.
  - `(push v e)` needs v to be a live, mutable `(vec T)` and e to be `T`, and has effect `alloc`.
  - All three add the effects of their expressions and apply their moves, left to right.
- **If-s:** the branches' Γ' are joined: a variable moved in either branch is moved.
- **While:** `(while c inv* (decreases d) body)`.
  - c is runtime `bool`; each inv is ghost `bool`; d is ghost `int`.
  - The body's normal exit Γ' must equal Γ on outer variables. Paths that return or panic are checked where they end.
  - The goals are in §9.
- **Call:**
  - Arguments are evaluated left to right and must match the callee's parameter types. An owned vector argument must be a live variable, which then moves. Any other expression there, such as `(vec-new)` or a `seq-build`, is `E-OWN-006` (D73). A slice parameter takes `(borrow v)`, or a slice parameter passed straight through.
  - Results bind with `(let ((x T) ...) (call f args))`, one name per declared result, in order. `(call f ...)` as a statement is only for a callee with no results, so dropping results is `E-TYPE-001` (D74).
  - Calls are modular. The caller proves ⟦callee requires⟧ with the arguments substituted, then assumes the callee's `ensures` with the arguments and the fresh result names substituted. It never sees the callee's body.
  - Effects are the callee's, plus those of the arguments.
  - A lemma call is a ghost statement with no effects, checked the same way. Its arguments are checked in ghost context, so `(call l (+ r 1))` passes an `int` and carries no overflow goal.
- **Return:** `(return e1 ... en)` checks each e against the corresponding declared result, left to right, moving owned vectors as it goes. A vector may appear in at most one of a return's expressions (`E-OWN-005`, §5), so `(return v v)` is rejected. ⟦ensures⟧ holds with the result names bound to the e's. A spec with no results is ended by `(return)`. Every path through a `def` body must end in `return` or `panic` (`E-RET-001`). For this check every `while` may end normally, whatever its condition, so a body that ends with a loop needs a `return` or `panic` after it. Statements after a `return` or `panic` are still checked for names and types, but being unreachable isn't an error (D77).
- **Ghost statements:**
  - `assert` adds ⟦e⟧ and then assumes e.
  - `ghost-let`, `ghost-let-mut` and `ghost-set` act on ghost locals only (§5, D75).

**Items:**
- A `spec`'s parameter types are runtime types. It may declare zero or more results, each `bool`, `i64` or `(vec T)`; a slice result is `E-OWN-002`, not a type error. Its results and parameters share D41's uniqueness (D66). `partition`, for example, returns its vector and a boundary index.
- `requires` and `ensures` are ghost `bool`. `ensures` may use the result names.
- Clauses are checked in order, each assuming the ones before it: `requires` first, then `ensures`, and likewise a loop's invariants. So a later clause may index with a value an earlier clause bounds.
- A `def` must name a spec in the same module. Its parameters and result are the spec's.
- A `lemma`'s body is in ghost context. It may contain only `assert`, `ghost-let`, `ghost-let-mut`, `ghost-set`, lemma calls, `if`, `block`, `while` over ghost locals, and `(return)`. A `return` with values is `E-GHOST-003`, like any other runtime statement there (D75). Statements take their context from where they appear: in ghost context, `if` and `while` take ghost conditions, and their bodies may contain only ghost statements. The `while` goals in §9 are the same in both contexts. From its `requires`, every path must establish its `ensures`, at each `(return)` and at the end of the body. A lemma with an empty body therefore proves only what follows from its `requires`.
- A `ghost-fn` is transparent: callers may unfold its body. The verifier proves its body well-defined under its `requires`, and that it terminates.
- Recursion is allowed only through the `decreases` of a `def`, `ghost-fn` or `lemma`. At each recursive call the verifier proves ⟦0 ≤ callee measure < caller measure⟧ under the callee's `requires`. Mutual recursion is rejected (`E-TERM-002`).

## 8. Dynamic semantics

The semantics is big-step over a store σ that maps names to values. Every value is a boolean, an i64, or a finite sequence of booleans or i64s. Vectors and slices are both sequence values; ownership only constrains which names may be used. Evaluation has three outcomes:
- **`ok(v1 ... vn, σ)`:** a normal result, holding one value per declared result. A result list is not itself a value, so B17-0 still has no tuples (§11): a list can only be bound by a call's `let`, one name per result.
- **`panic`:** from `(panic STR)`.
- **`err`:** arithmetic leaving i64, an index out of range, division by zero, or a negative `seq-build` length.

`err` is a stuck state: the verifier must prove it unreachable. The soundness theorem WP1b will mechanize in Lean (D16) is that a program that type-checks and has every goal discharged never reaches `err`, and that every normal return satisfies its `ensures`.

**Operations:**
- **Integers:** runtime arithmetic is i64 arithmetic restricted to the cases Rust's checked operations accept; anything else is `err`. Division truncates toward zero, and `%` takes the sign of the dividend.
- **Logic:** `and`, `or` and `=>` short-circuit, as described in §7.
- **`push`:** appends to the sequence. **`set-idx`:** replaces one element.
- **`print`:** appends to an output trace that is part of the observable result.

These rules match safe Rust (D18): an i64 operation that would panic in Rust is `err` here, and a verified program never performs one.

## 9. Proof goals

`b17c` generates one goal per obligation and sends each to Z3 as its own query (D17). A verdict means every goal passes under the canonical seed and under N shuffled seeds (D23). Each goal carries the node ID of the expression it came from and a code from the families below, which WP6 will refine.

| Family | Goal |
|---|---|
| `E-PROOF-BOUNDS` | An index, `take`, `drop` or `last` is in range |
| `E-PROOF-OVERFLOW` | A runtime arithmetic or negation result fits in i64 |
| `E-PROOF-DIV` | A divisor is not zero, and not −1 when the dividend is −2^63 |
| `E-PROOF-PRE` | A call's or ghost-fn's `requires` holds |
| `E-PROOF-INV-ENTRY` | A loop invariant holds on entry |
| `E-PROOF-INV-KEEP` | One iteration preserves the invariants |
| `E-PROOF-TERM` | A loop's measure is ≥ 0 whenever its condition holds, and strictly decreases across each normal pass through the body; at each recursive call, 0 ≤ callee measure < caller measure |
| `E-PROOF-POST` | `ensures` holds at each `return`, and at the end of each `lemma` body |
| `E-PROOF-ASSERT` | An `assert` holds |

**How goals are generated:** by weakest preconditions over the statements, using the standard rule for `while`. Every goal is assumed once it has been generated, as `assert` is (§7), so a program with one wrong step reports that step's goal and not its consequences. That rule checks the invariants on entry, checks that one arbitrary iteration starting from the invariants and the condition preserves them and decreases the measure, and continues after the loop from the invariants and the negated condition. Goals inside a loop body are proven under the invariants.

Each statement has three exits: normal, `return` and `panic`.
- `wp((return e1 ... en), Q) = ensures[results := e1 ... en]`: a `return` proves `ensures` where it stands and ignores Q.
- `wp((panic STR), Q) = true`.
- After a call, the caller assumes the callee's `ensures` (§7).

The `while` rule written out, with I the invariants, c the condition and d the measure:
- **On entry:** I holds, along with c's own goals (bounds, overflow, and so on).
- **At every iteration start:** from I, c's goals hold.
- **For one arbitrary iteration:** from I and c, with d0 the value of d, prove `0 ≤ d0` and `wp(body, I ∧ d < d0)`.
- **After the loop:** continue from I and not c.
- **What an iteration forgets:** at the start of an arbitrary iteration, only the variables the body can change are unknown: those it assigns with `set`, `set-idx`, `push` or `ghost-set`, or moves. Facts about every other variable still hold.

Invariant preservation and the measure decrease apply only to the body's normal exit; returns and panics inside the body follow their own rules above.

**Encoding (D61):**
- **Sequences:** vectors, slices and seqs are an uninterpreted sort per element type, whose only axioms are the background facts below, with triggers. SMT-LIB's sequence theory isn't used. The prefix step fact is instantiated at each `take` term the generator creates, since as a trigger it would loop.
- **Multisets:** count maps.
- **Division:** `/` and `%` by a divisor that isn't a literal are uninterpreted, with D37's truncation facts as axioms.
- **Recursive ghost-fns:** each one's defining equation holds under its `requires` only, and is left out of the ghost-fn's own goals.
- **Budget:** every goal runs under a resource budget, never a time limit (D23).

**The core library (WP16, D28)** is implicitly in scope in every B17-0 module, since imports wait for the lockfile (D9, D26). It contains:
- the ghost-fn `sorted`, defined as `(ghost-fn sorted ((s (seq int))) bool (body (forall ((i int) (j int)) (=> (and (and (<= 0 i) (< i j)) (< j (len s))) (<= (idx s i) (idx s j))))))`;
- the ghost-fn `in_i64`, true when an `int` lies in [−2^63, 2^63), for stating ranges (§10);
- the laws of integer order;
- the background facts below, which are the whole of what a proof may use about collections beyond the definitions in §7. Dafny made agents assert several of them by hand, such as `take(s, i+1) == concat(take(s, i), [s[i]])`.

**Background facts.** For sequences s and t, indices i and k in range, and values x and e:
- **Ranges:** every `i64` value lies in [−2^63, 2^63), and every vector or slice length in [0, 2^63). Growing a vector past that is an allocation failure, which aborts (§6).
- **Length:** `len (seq-lit e1 … en) = n`, `len (concat s t) = len s + len t`, `len (take s k) = k` and `len (drop s k) = len s − k`.
- **Elements:**
  - `idx (concat s t) i` is `idx s i` when i < `len s`, and `idx t (i − len s)` otherwise;
  - `idx (take s k) i = idx s i`;
  - `idx (drop s k) i = idx s (i + k)`;
  - `last s = idx s (len s − 1)`.
- **Prefixes:**
  - `take s (len s) = s`;
  - `take s 0` is empty;
  - `take (take s k) j = take s j` for j ≤ k;
  - `take s (i + 1) = concat (take s i) (seq-lit (idx s i))`.
- **Equality:** sequences are equal when their lengths and elements are; multisets are equal when every count is.
- **Membership:** `contains s x` holds exactly when some `idx s i = x`. It follows that `contains (concat s t) x` is `contains s x` or `contains t x`, that `(seq-lit y)` contains only y, and that the empty sequence contains nothing. These are stated as facts too (D61).
- **Multisets:**
  - `occurrences s x` is the count of x in `multiset s`;
  - `multiset (concat s t) = msum (multiset s) (multiset t)`;
  - `msum` adds counts;
  - the multiset of `(seq-lit x)` counts x once and nothing else, and the empty sequence's multiset is empty.
- **Updates:**
  - after `(set-idx v i e)`, v has the same length, `idx v i = e` and every other element is unchanged, and its multiset loses one count of the old `idx v i` and gains one of e;
  - after `(push v e)`, v is `concat v (seq-lit e)`.

Integer reasoning is the solver's linear arithmetic, plus whatever nonlinear facts it proves on its own.

Its names are reserved. Its facts are axioms of the encoding, so they're listed in the trusted base report until the kernel exists (D24).

**Tier 0 errors** are reported before any goal is generated. WP6 will refine the codes; these are the ones the suite (§12) uses.

| Code | Error |
|---|---|
| `E-PARSE-001` | Not a term of the grammar in §2, or against its reading rules, such as a `while` with no `decreases` or a grammar word used as a name |
| `E-TYPE-001` | A type mismatch, or a name of the wrong kind (D67): an item used as a value, a spec or lemma called as `(NAME e*)`, a ghost-fn called with `call` in ghost code, or a parameter, local or binder called either way |
| `E-TYPE-002` | A name error: undefined, a core library name declared again (D51), or reused against §2's rules (D41), including a `def` with no `spec`, or a spec identical to another up to names (D45) |
| `E-GHOST-001` | A ghost binding used in runtime context (Var-R) |
| `E-GHOST-002` | A ghost type, ghost-only operation or ghost-fn call in runtime context, in whatever form the call is written (D67) |
| `E-GHOST-003` | A runtime statement in ghost context, such as a `def` call, `let`, `push`, `print` or `panic` in a lemma |
| `E-OWN-001` to `E-OWN-006` | The ownership rules, §5 and §7 |
| `E-EFF-001` | A `def` body's effects exceed its spec's |
| `E-RET-001` | A path through a `def` body that doesn't end in `return` or `panic` |
| `E-TERM-001` | A recursive call from an item with no `decreases` |
| `E-TERM-002` | Mutual recursion |

**One diagnostic per error (D78).** Every independent error is reported, and none that merely follows from another:
- **Failed expressions:** an expression that fails a check takes a type compatible with anything, so code that uses it doesn't report again.
- **Names declared wrongly:** an item name declared twice, a core library name declared again, or a `def` with no spec is reported once, at the later declaration. Uses of that name aren't checked, and neither is the orphan `def`'s body, since its spec would supply its parameters (D67). A local declared twice keeps the binding already in scope.
- **Moves:** a moved vector's first runtime use is reported (`E-OWN-001`), and later ones aren't. A vector repeated in one call or return is reported once (`E-OWN-005`), with no use-after-move report on top.
- **Effects:** each effect a spec leaves out is reported once, at the first statement that has it (`E-EFF-001`).
- **Recursion:** `E-TERM-001` is reported at each recursive call. `E-TERM-002` is reported once per group of mutually recursive items, a strongly connected component of the call graph, at its first call.
- **Duplicate specs:** D45's check runs last, only once nothing else has failed, and reports `E-TYPE-002` at the later spec.

Each diagnostic gives the line and column of the form it's about (§2), until WP6 defines node IDs.

## 10. How a task is posed

A task gives the agent three things:
- a module header;
- the frozen `ghost-fn`s;
- the frozen `spec`.

The agent returns a `def` for that spec. It may add `lemma`s, `ghost-fn`s, and `spec` and `def` pairs for helpers.

The task's spec is frozen by construction: the agent never writes it, so it can't weaken it. That replaces the generated `_Check` wrapper the Dafny harness needs. A helper spec belongs to the agent and binds only the agent's own code.

`assume` doesn't exist in B17-0. When `admit` arrives (Verification model), it will be counted in the trusted base report and will score zero in the gym.

**Porting tasks:** tasks ported to B17-0 must state ranges that Dafny's unbounded `int` never needed (D42). The rule: a task requires every value its computation produces to fit in i64, stated per loop step in the terms that step uses (D60). `fib` requires `(forall ((i int)) (=> (and (<= 1 i) (< i n)) (in_i64 (+ (fib (- i 1)) (fib i)))))`, and `sum` requires the same of each partial sum plus its next element. Given each ghost-fn's definition, this admits exactly the inputs that "every `fib i` for `i <= n` fits" does. But a step's overflow goal needs the range at the next index, a term the program never mentions before the step, so only the step form proves without hints. `(<= n 92)` states the same range for `fib`, but a proof from it has to evaluate fib(92). The Dafny baseline versions get the same preconditions, so the two task sets stay aligned and only the language differs. The extra goals this creates are what Bet 1 ("rigor is cheap for machines") claims costs agents little, and M3 measures it.

## 12. Accept/reject suite

WP1a's done-when needs a suite of labelled programs.

**Accept:** the 20 seed tasks ported to B17-0, plus the worked example.

**Reject:** at least one program per error code in §7 and §9, each labelled with its expected code. Examples:
- a vector used after a move;
- a vector produced by an `if` expression;
- a loop condition that indexes out of bounds;
- a returned slice;
- a slice stored in a `let`;
- `push` in a function without `alloc`;
- a ghost-fn call in runtime code;
- `i64` overflow in `(+ x 1)` without a bound;
- a missing `decreases`;
- mutual recursion;
- a path that doesn't return.

Each program carries its expected verdict and code. WP3's checker and WP15's interpreter must agree with every one. The suite is in `suite/`; its README gives the layout.

## 13. Decisions

These are entries D33–D43 in `DECISIONS.md`, accepted on 2026-10-27.

- **D33:** B17-0's canonical S-expression form is also its core language, so there is no separate elaboration step. WP3 is a checker, not an elaborator, until a richer surface exists.
- **D34:** Runtime integers are `i64`, and every operation's range is a proof goal. Ghost integers are unbounded `int`. `i64 <: int` holds in ghost context only. There are no implicit runtime conversions.
- **D35:** B17-0 has no vector capacity, so this supersedes only D29's capacity clause: the `capacity(out) >= len(a) + len(b)` invariant waits for allocation bounds (D30), and `vec-with-capacity` is dropped from the subset. D29's other clauses stand; the worked example keeps its length precondition.
- **D36:** Ownership without lifetimes:
  - vectors are owned and move;
  - slices are call-scoped shared borrows that can't be stored or returned;
  - there is no `&mut`;
  - in-place algorithms take ownership and return it.
- **D37:** Division truncates toward zero in both contexts, as in Rust, not Euclidean as in Dafny.
- **D38:** `seq-build` binds its index with `0 <= i < n` assumed. This is the first language change driven by a measured agent failure (WP17: Codex's `reverse`, 6 of 6 first attempts).
- **D39:** A `def` implements a named `spec` and never restates it. Tasks give agents the frozen spec, so contracts can't be weakened by construction.
- **D40:** Every `def` path ends in `return` or `panic`, and early returns are allowed. There is one way to exit with results: `(return e1 ... en)`, one expression per declared result.
- **D41:** No shadowing. Item names are unique within a module, except that a `spec` and its `def` share one name. Local names are unique within their item.
- **D42:** Ported tasks state explicit integer ranges, and the Dafny baselines take the same preconditions, so task sets stay aligned across languages.
- **D43:** A spec may declare several results, returned together by `(return e1 ... en)` and bound by `(let ((x T) ...) (call ...))`. Owned-in, owned-out algorithms that also compute something, such as `partition`, need this.
